1. Entity Relationship Diagram (ERD) — [2 Marks]

1.1 Project Domain Rationale & Guide-Approved Approach

As established during the synopsis defense with project guide Dr Hemanth K S, tracking faculty members via physical biometric NFC/RFID scanners across every campus door is technically difficult, prone to sensor downtime, and invasive. To solve this pragmatically, UniChrist incorporates an intelligent Automated Faculty Schedule & Location Engine directly within the relational database. The engine dynamically evaluates weekly faculty timetables against wall-clock time: if a lecture is active, students see the real-time classroom (e.g. Lab 201 - DBMS Lab); if free, the system routes students to their designated cabin (e.g. Staff Room 304). The ER diagram models this together with cafeteria pre-ordering, parking telemetry, grievance tracking, and library circulation.

1.2 Entity Identification & Structural Attribute Classification

The proposed relational database models 21 distinct entity sets:

  • Users & Academic Hierarchy: ROLES, USERS, STUDENTS, FACULTIES, SCHOOLS, DEPARTMENTS.
  • Campus Spatial & Schedule Engine: CAMPUS_BLOCKS, CAMPUS_ROOMS, FACULTY_TIMETABLES, FACULTY_STATUS_OVERRIDES.
  • Smart Cafeteria & Pre-Ordering: CAFETERIA_VENDORS, CAFETERIA_ITEMS, CAFETERIA_ORDERS, CAFETERIA_ORDER_ITEMS.
  • Campus Utilities & Telemetry: PARKING_SLOTS, PARKING_LOGS, GRIEVANCES, GRIEVANCE_AUDIT_LOGS, BOOK_CATEGORIES, LIBRARY_BOOKS, LIBRARY_CIRCULATION.

2. Database Normalization (UNF to BCNF) — [3 Marks]

2.1 Theoretical Foundations & Operational Anomalies

Normalization is an algebraic and relational design discipline that prevents undesirable operational anomalies:

  • Insertion Anomaly: Occurs when a piece of data cannot be inserted without the presence of unrelated attributes. In UniChrist, if faculties and classrooms were kept in a single relation, a newly constructed computer lab could not be entered until a class was scheduled in it.
  • Deletion Anomaly: Occurs when deleting one fact inadvertently destroys completely different facts. For instance, if an elective course is dropped and its timetable row deleted, erasing the faculty's cabin room and designation.
  • Update Anomaly: Occurs when redundant data is updated in one row but remains unchanged in others, leading to relational schizophrenia and broken integrity.

2.2 Step-by-Step Normalization: Faculty Spatial Timetable Engine

Stage 0: Unnormalized Form (UNF)

UNF_FACULTY_SCHEDULE_FLAT (
    faculty_reg_no, faculty_name, dept_name, hod_name, designation,
    cabin_block, cabin_room, consultation_hours,
    day_of_week, period_number, start_time, end_time,
    course_code, course_name, lecture_room_number, lecture_block_name,
    seating_capacity, class_section
)

Deficiencies: Multi-period repeating groups exist; non-atomic lists of periods are stored per faculty member.

Stage 1: First Normal Form (1NF)

Transformation: Expand repeating period groups so that every attribute contains only atomic (indivisible) values from its domain. Define the composite candidate key:

Primary Key Candidate: {faculty_reg_no, day_of_week, period_number}

R_1NF (
    faculty_reg_no [PK], day_of_week [PK], period_number [PK],
    faculty_name, dept_name, hod_name, designation,
    cabin_block, cabin_room, consultation_hours,
    start_time, end_time, course_code, course_name,
    lecture_room_number, lecture_block_name, seating_capacity, class_section
)

Stage 2: Second Normal Form (2NF)

Rule: The relation must be in 1NF and contain no partial dependencies (every non-prime attribute must depend on the whole candidate key, not a proper subset).

Identified Functional Dependencies:

  • $FD_1: \{ ext{faculty\_reg\_no}\} ightarrow \{ ext{faculty\_name}, ext{dept\_name}, ext{hod\_name}, ext{designation}, ext{cabin\_block}, ext{cabin\_room}, ext{consultation\_hours}\}$ ⇒ Partial Dependency! Depends only on faculty_reg_no, not on day_of_week or period_number.
  • $FD_2: \{ ext{faculty\_reg\_no}, ext{day\_of\_week}, ext{period\_number}\} ightarrow \{ ext{start\_time}, ext{end\_time}, ext{course\_code}, ext{course\_name}, ext{lecture\_room\_number}, ext{class\_section}\}$ ⇒ Full Dependency.
  • $FD_3: \{ ext{lecture\_room\_number}, ext{lecture\_block\_name}\} ightarrow \{ ext{seating\_capacity}\}$ ⇒ Independent of faculty.

Decomposition into 2NF Relations:

R_FACULTY_2NF (faculty_id [PK], faculty_name, dept_name, hod_name, designation, cabin_block, cabin_room, consultation_hours)
R_ROOM_2NF (room_id [PK], block_name, room_number, seating_capacity)
R_TIMETABLE_2NF (schedule_id [PK], faculty_id [FK], day_of_week, period_number, start_time, end_time, room_id [FK], course_code, course_name, class_section)

Stage 3: Third Normal Form (3NF)

Rule: The relation must be in 2NF and contain no transitive dependencies (non-prime attributes must not determine other non-prime attributes: if $X ightarrow Y$ and $Y ightarrow Z$, then $Y$ must be a superkey).

Transitive Violations in 2NF Relations:

  • In R_FACULTY_2NF: $ ext{faculty\_id} ightarrow ext{dept\_name}$ and $ ext{dept\_name} ightarrow ext{hod\_name}$. Hence $ ext{faculty\_id} ightarrow ext{hod\_name}$ is transitive!
  • In R_ROOM_2NF: $ ext{room\_id} ightarrow ext{block\_name}$ and $ ext{block\_name} ightarrow ext{total\_floors}$.

Decomposition into 3NF Relations:

Departments (dept_id [PK], school_id [FK], dept_name, hod_name)
Faculties (faculty_id [PK/FK], dept_id [FK], designation, cabin_room_id [FK], consultation_hours)
Campus_Blocks (block_id [PK], block_code, block_name, total_floors)
Campus_Rooms (room_id [PK], block_id [FK], room_number, floor_number, room_type, seating_capacity)
Faculty_Timetables (schedule_id [PK], faculty_id [FK], day_of_week, period_number, start_time, end_time, room_id [FK], course_code, course_name, class_section)

Stage 4: Boyce-Codd Normal Form (BCNF) Verification

Formal Test: For every non-trivial functional dependency $X ightarrow Y$ in the relation, the determinant $X$ must be a Superkey.

Let us evaluate Faculty_Timetables:

  • Candidate Key 1: schedule_id
  • Candidate Key 2: {faculty_id, day_of_week, period_number}
  • Candidate Key 3: {room_id, day_of_week, period_number}

Every non-trivial FD has a left-hand side (determinant) that is a full candidate key. No non-superkey determinants exist. Therefore, the decomposed relation is strictly in Boyce-Codd Normal Form (BCNF).

3. Relational Database Schema & Data Dictionary — [2 Marks]

3.1 Transformation Rules: ERD to Relational Tables

  1. Strong Entity Sets: Each strong entity converts directly to an independent relational table with its conceptual primary key as the table's Primary Key.
  2. Specialization Hierarchies (Users → Students / Faculties): Modeled using separate sub-type tables where the primary key of the sub-type is also a Foreign Key pointing to Users.user_id (1:1 referential integrity).
  3. 1:N Relationships: Propagated by placing the Primary Key of the "1" side as a Foreign Key inside the "N" side table.
  4. M:N Relationships (Orders ↔ Items, Books ↔ Users): Decomposed into dedicated associative tables (Cafeteria_Order_Items, Library_Circulation) containing foreign keys from both participating tables.

4. Database Creation and Data Population — [3 Marks]

4.1 Full SQL Schema DDL (Table Creation Scripts)

CREATE TABLE Roles (
    role_id INT AUTO_INCREMENT PRIMARY KEY,
    role_name VARCHAR(50) NOT NULL UNIQUE,
    role_description VARCHAR(255)
);

CREATE TABLE Campus_Blocks (
    block_id INT AUTO_INCREMENT PRIMARY KEY,
    block_code VARCHAR(20) NOT NULL UNIQUE,
    block_name VARCHAR(100) NOT NULL,
    total_floors INT NOT NULL CHECK (total_floors > 0),
    latitude DECIMAL(9,6), longitude DECIMAL(9,6)
);

CREATE TABLE Campus_Rooms (
    room_id INT AUTO_INCREMENT PRIMARY KEY,
    block_id INT NOT NULL REFERENCES Campus_Blocks(block_id) ON DELETE CASCADE,
    room_number VARCHAR(30) NOT NULL,
    floor_number INT NOT NULL,
    room_type VARCHAR(50) NOT NULL CHECK (room_type IN ('CLASSROOM', 'LAB', 'STAFF_ROOM', 'SEMINAR_HALL', 'AUDITORIUM', 'OFFICE', 'LIBRARY', 'INFIRMARY')),
    seating_capacity INT DEFAULT 60 CHECK (seating_capacity >= 0),
    is_active BOOLEAN DEFAULT TRUE,
    UNIQUE KEY uq_block_room (block_id, room_number)
);

CREATE TABLE Users (
    user_id INT AUTO_INCREMENT PRIMARY KEY,
    role_id INT NOT NULL REFERENCES Roles(role_id) ON DELETE RESTRICT,
    register_number VARCHAR(50) NOT NULL UNIQUE,
    full_name VARCHAR(120) NOT NULL,
    email VARCHAR(120) NOT NULL UNIQUE CHECK (email LIKE '%@%'),
    password_hash VARCHAR(255) NOT NULL,
    phone_number VARCHAR(20),
    is_active BOOLEAN NOT NULL DEFAULT TRUE,
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE Faculties (
    faculty_id INT PRIMARY KEY REFERENCES Users(user_id) ON DELETE CASCADE,
    dept_id INT NOT NULL REFERENCES Departments(dept_id) ON DELETE RESTRICT,
    designation VARCHAR(80) NOT NULL,
    cabin_room_id INT REFERENCES Campus_Rooms(room_id) ON DELETE SET NULL,
    office_extension VARCHAR(20),
    consultation_hours VARCHAR(100)
);

CREATE TABLE Faculty_Timetables (
    schedule_id INT AUTO_INCREMENT PRIMARY KEY,
    faculty_id INT NOT NULL REFERENCES Faculties(faculty_id) ON DELETE CASCADE,
    day_of_week VARCHAR(15) NOT NULL CHECK (day_of_week IN ('MONDAY', 'TUESDAY', 'WEDNESDAY', 'THURSDAY', 'FRIDAY', 'SATURDAY')),
    period_number INT NOT NULL CHECK (period_number BETWEEN 1 AND 8),
    start_time TIME NOT NULL, end_time TIME NOT NULL CHECK (end_time > start_time),
    room_id INT NOT NULL REFERENCES Campus_Rooms(room_id) ON DELETE RESTRICT,
    course_code VARCHAR(30) NOT NULL, course_name VARCHAR(120) NOT NULL, class_section VARCHAR(20) NOT NULL,
    UNIQUE KEY uq_faculty_period (faculty_id, day_of_week, period_number),
    UNIQUE KEY uq_room_period (room_id, day_of_week, period_number)
);
